## Why

The connections page has two log windows — DE1 on the left, scale on the right — and each is backed by its own private channel instead of the log we actually collect. Both are worth removing, for different reasons.

**The scale log is a duplicate store.** Scale lines are recorded into `BLEManager::m_scaleLogMessages` (a 1000-entry ring, exported as a shareable `scale_debug_log.txt`) *and* written to the system log by the source that emitted them. That duplication is the direct cause of a run of defects: the double-printing fixed in #1700, the 21 USB call sites where the `qDebug` and the `logMessage` had drifted into describing one event in different words, and the `[Scale]` grep that silently stopped covering driver lines when the duplicate mirror was removed. We stopped asking users for `scale_debug_log.txt` some time ago and now ask only for the system log, so the second store is maintained for exactly one on-screen view.

**The DE1 log is worse — it is a store with no persistence at all.** `de1LogMessage` is a bare signal with no backing buffer, and its 17 emitters in `blemanager.cpp` write to *nothing else*. The permission flow, scan lifecycle and direct-wake decisions it narrates have never appeared in a submitted log; they exist only in a live window, and only while the Connections tab happens to be open. Alongside that, DE1 stderr logging is spread across four prefix families (`[BLE DE1]` ×10, `[USB]` ×62, `[DE1]` ×1, and ~33 unprefixed lines in `de1device.cpp`), with helpers in `BleTransport` but none in `SerialTransport` or `UsbManager` — the same hand-rolled-prefix drift the scale side just had removed.

The machinery to replace both already exists: `WebDebugLogger` records session boundaries, `McpLogFilter` does substring/regex/level filtering with dedupe and pagination, and the `[Scale]` marker work proved the pattern — one reliable token per subsystem is all a filtered view needs.

## What Changes

**One log, two filtered views.**

- **BREAKING (internal API):** Remove both private channels. Scale: `appendScaleLog()`, `m_scaleLogMessages`, `writeScaleLogToFile()`, `clearScaleLog()`, `shareScaleLog()`, `getScaleLogPath()`, the `scaleLogMessage` signal and the `mirrorToSystemLog` parameter. DE1: the `de1LogMessage` signal. Callers log once, to the system log, through their subsystem's helper.
- Both windows are **kept** and re-sourced: each shows the current session's lines for its subsystem, filtered out of the system log by a marker — `[Scale]` plus `[Refractometer]` for the scale window, `[DE1]` for the DE1 window — **at INFO or above**.
- **Severity becomes the audience axis.** The helpers gain an INFO tier between the existing debug and warning ones, and every call site is assigned a tier: frame-level driver and transport detail stays DEBUG, the connection narrative a user might need becomes INFO, problems stay WARN. The windows show INFO and above, so they carry the curated narrative and not the firehose. This reuses the `minLevel` machinery the MCP tools already have rather than adding a second prefix token — a new prefix family is exactly what the preceding work removed.
- **The two windows converge on the DE1 window's character.** Today the DE1 window is a curated 17 lines while the scale window also carries every driver and transport debug line. After this the scale window is quieter: driver detail remains in the system log, greppable and one MCP argument away, but off the panel.
- Both views gain what the old ones could not have: they survive a page revisit (the old ones accumulated only lines that arrived while the tab was built) and can show lines from before the tab was opened. For DE1 this is the first time those lines are recoverable at all.
- **DE1 logging is centralized the way the scale side now is.** `[DE1]` becomes the marker, applied in helpers, never at a call site: `SerialTransport` and `UsbManager` get `log()`/`warn()` helpers they currently lack, `BleTransport`'s existing helpers gain the marker, `de1device.cpp`'s hand-rolled prefixes and unprefixed lines route through one, and the DE1-over-USB `[USB]` family becomes `[DE1][USB]`. The 17 signal-only lines in `blemanager.cpp` become real log calls.
- **Clear** stops meaning "erase the log" and becomes view-local — it hides what is shown and keeps following new lines. Clearing a shared diagnostic store from a device panel is not a behaviour worth carrying over.
- **Share** is retargeted from `scale_debug_log.txt` to the system log, so the button hands over the artifact we actually ask for. `scale_debug_log.txt` is no longer produced.
- `WebDebugLogger` gains a line-appended signal, a session-scoped filtered accessor, and QML exposure (compile-time registration, per `QML_GOTCHAS.md`). It has none of these today, which is why nothing but the private channels could feed an on-screen view.
- MCP `debug_get_log` gains **no new parameter** — `filter` plus `minLevel` already express "what the scale panel shows" in one call. What it gains is a description that names the `[Scale]`/`[DE1]` markers and the tier convention, since an undocumented token is discoverable only by reading source, plus the warning that a bracketed marker must be passed as a substring (under `regex: true` it is a character class matching almost every line, failing by returning too much rather than erroring).
- **Three markers, not two.** `[Scale]`, `[DE1]` and `[Refractometer]` — the R1/R2 share the scale BLE transports but are a different instrument, so a TDS complaint and a weight complaint are searchable apart from each other. They stay in the scale window (which shows both markers), because that is where they live on screen; the separation is for querying, not for the UI.
- **The token scheme becomes a documented, reusable convention rather than two ad-hoc markers.** A `[Subsystem]` marker plus optional `[Subsystem][Source]` detail, three severity tiers carrying audience, applied only inside helpers. Scale and DE1 are its first two subjects; the point is that the next subsystem registers a marker and gets a filterable view and an MCP query for free instead of inventing a fifth prefix family.
- **The marker list lives in exactly one place** — a registry in code — and the MCP tool description, the docs and the enforcement check all derive from it. Writing the list into a tool description, a reference doc and a lint script would be three copies of the thing this change exists to stop.
- Subsystem sources SHALL carry their marker and SHALL choose a tier deliberately. Both halves of the filter are only sound while that holds: a new helper without the marker, or a user-facing line left at DEBUG, silently drops out of its view and out of every log query that names the subsystem. A source-level check enforces it rather than relying on review.

## Capabilities

### New Capabilities
- `log-tagging-convention`: The reusable scheme — marker grammar, the three audience tiers, helper-only application, the single registry the tool description/docs/check all derive from, and what registering a new subsystem requires. Applies beyond the two subsystems this change converts.
- `device-log-views`: The DE1 and scale log windows as filtered views over the single system log — what each shows (current session, marker at INFO+), population and live-follow, view-local clear, share target. Also covers removal of the two private channels and the centralization of DE1 logging behind helpers.

### Modified Capabilities
- `mcp-server`: The existing "Debug log tools support substring/regex filtering" requirement gains a documentation guarantee — the tool description must name the registered subsystem markers (derived from the registry, not restated), the tier convention, and the marker-as-regex trap. No parameter is added.
- `wifi-scale-discovery`: Five scenarios assert outcomes are recorded in "the scale log". The recording requirement is unchanged in substance, but the store it names will not exist; re-worded to the system log and its scale-filtered view.

## Impact

- **Removed:** `scale_debug_log.txt` as a produced artifact. Anywhere we still ask users for it (support notes, the wiki manual) must ask for the system log instead — the manual needs checking as part of this change.
- **Code:** `src/ble/blemanager.{h,cpp}` (both channels removed; ~60 `appendScaleLog` and 17 `de1LogMessage` sites become helper calls), `src/ble/de1device.cpp`, `src/ble/bletransport.cpp`, `src/usb/usbmanager.cpp`, `src/usb/serialtransport.cpp` (DE1 marker + helpers, ~84 stderr sites), `src/network/webdebuglogger.{h,cpp}` (signal, filtered accessor, QML exposure), `qml/pages/settings/SettingsConnectionsTab.qml` (both views, clear, share), `src/mcp/mcpresources.cpp` (`debug_get_log` description only — no filter-code change; `McpLogFilter` already does everything needed).
- **Depends on** the `[Scale]` marker unification (PR #1703, open). It establishes the pattern the DE1 half copies, and without one reliable scale token the scale filter cannot be written.
- **Risk — tier assignment is the whole change.** ~100 call sites each need a deliberate tier, and both directions of error are silent: a user-facing line left at DEBUG disappears from its window, and driver chatter promoted to INFO reintroduces the noise this is meant to remove. Existing `qWarning` sites must not be demoted either — they are findable today via `minLevel: WARN`.
- **Risk — `QTest::failOnWarning()`.** Several suites use it, so any site that gains WARN where it previously had none will fail tests that traverse that path. INFO is not affected.
- **Risk — the shared log is busier.** Both views must filter the *current session* only, or a long-lived log makes the window useless.
- **New:** a marker registry in code, a `docs/CLAUDE_MD/LOGGING.md` reference (listed in the CLAUDE.md table) describing the convention for future work, and a source-level check that every device logging helper applies a registered marker.
- **Tests:** `tst_webdebuglogger` and `tst_mcplogfilter` are the natural homes for the accessor and filter behaviour, and the registry-derived description is assertable. The QML views are manual-test-only per project convention, so the marker contract needs the source-level guard rather than a view test.
