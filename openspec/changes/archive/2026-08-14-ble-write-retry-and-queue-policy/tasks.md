## 3. Supersede

- [x] 3.1 At the upload-supersede point already detected in `DE1Device::startProfileUploadTracking()` (`src/ble/de1device.cpp:1324-1326`), which currently does nothing to the transport queue, discard **the previous upload's** pending writes. This is the narrowest fix for the #1466 cascade.
- [x] 3.2 Do **not** implement it as `clearQueue()`. Both references supersede per-kind: de1app's `remove_matching_ble_queue_entries` (`de1_comms.tcl:1423`) is called at 14 sites, including `{^Espresso header:}` / `{^Espresso frame #}` at `:1487-88`, always by the producer immediately before enqueueing the replacement; decaid never enqueues the superseded upload at all (`workflow_device_sync.dart:113-127`). A blanket clear also discards unrelated pending work, which is not superseded by anything.
- [x] 3.3 Scoped: small. `queueCommand()` has exactly two call sites (`write()` and `read()`), both with the UUID already in scope, so the queue element became `struct QueuedCommand { QBluetoothUuid uuid; std::function<void()> run; }` and nothing else moved. `HEADER_WRITE`/`FRAME_WRITE` carry profile frames and nothing else, so the characteristic alone identifies the operation's work — no owner token needed. DE1Device-level tracking was therefore not required.
- [x] 3.4 Pair the discard with `m_lastMMRValues` invalidation, as `clearCommandQueue()` already does (`de1device.cpp:1243-1261`) — without it the dedup cache elides the re-send and a discarded setting is lost, not delayed.
- [x] 3.5 Log the discard and the number discarded.
- [x] 3.6 Assert, don't build: confirm by test that a commanded stop is delivered across a discard. The current ordering already guarantees it — `stopOperationUrgent`/`sleep` clear before writing (`de1device.cpp:1174`, `:1228`) and `clearQueue()` sets `m_writePending = false` (`bletransport.cpp:399`), so the urgent write takes the direct branch and is never queued at clear time. Neither reference has any priority concept; do **not** add a priority queue.
- [x] 3.7 Discard the failed upload's own frames in `finishProfileUpload(success=false)` too — see §4.1, this is the actual #1466 mechanism. Do **not** discard *unrelated* work on terminal write failure. Removed from this change after the reference comparison: Decenza today continues to the next command (`bletransport.cpp:148`, `:741`), de1app clears only on connect/disconnect (`de1_comms.tcl:247-248`, `:629-630`), and decaid's clear-on-timeout is about the **platform** operation queue where a stuck entry blocks every following op (`universal_ble_transport.dart:409-415`) — a constraint Decenza's app-level queue does not have. Nothing in the corpus shows harm from the writes behind a failure.
- [x] 3.8 Tests in `tst_bletransporterror.cpp` / the DE1Device tests: a supersede discards the previous upload's writes; unrelated pending writes survive it; a write abandoned after retries does **not** discard what is queued behind it; a discarded MMR value is actually re-sent afterwards rather than elided; a commanded stop is delivered across a discard.

## 4. Upload retry gating

- [x] 4.1 **The in-flight guard already exists and was never the bug.** `ProfileManager` refuses to start an upload while one is in flight (`m_uploadInFlight`, `profilemanager.cpp:2176`, set at `:2184`, cleared only in the `profileUploaded` handler at `:186`), and it arms the retry timer only from inside that handler (`:247`). A retry therefore cannot overlap the *attempt*. What it overlaps is the attempt's **writes**: `m_uploadTimeoutTimer` is 10 s (`de1device.cpp:79`) while a timing-out write occupied the link for far longer, so the tracker gave up, released the gate, and the retry was issued into a queue still holding every frame of the attempt just declared failed. Fixed by §3.7 (withdraw the failed upload's frames), not by guarding harder upstream. Recorded here because the first draft of this change specified the wrong fix from a correct diagnosis of the symptom.
- [x] 4.2 Verify by test that a retry issued after a *timed-out* upload finds no frames from the previous attempt queued. This is the assertion §4 is actually worth; the guard itself is already covered.
- [ ] 4.3 Consider abandoning an outstanding retry sequence when the operation is superseded — decaid's `_generation` guard (`workflow_device_sync.dart`) exists for exactly this and Decenza has no equivalent. Lower value now that the queue no longer carries the dead attempt; decide deliberately rather than by omission.
